# Hyphae — MVP (тонкий срез)

> Этот документ — про **минимальный вертикальный срез** Hyphae: что входит в первый работающий кусок, что явно отрезано и почему. Полный продукт и roadmap — в [SPEC_RU.md](./SPEC_RU.md). Концепция модели (оси, профили, анти-избыточность) — в [MODEL_RU.md](./MODEL_RU.md).

---

## 1. Гипотеза среза

Срез доказывает **одну** вещь:

> Человек ведёт архитектурную модель в визуальном редакторе → LLM-агент читает её через MCP → это реально полезно при работе с кодом.

Это главная ставка проекта (см. SPEC_RU §1, §8). Всё остальное в MVP подчинено проверке именно этого. Если гипотеза не подтверждается — богатый редактор и многоуровневость не спасут.

**Стратегия: вертикаль, не горизонталь.** Берём узкий набор сущностей, но проводим его end-to-end вплоть до потребления LLM. Лучше тонкая работающая цепочка человек→модель→LLM, чем широкий редактор без выхода на AI.

---

## 2. Критерии готовности (Definition of Done)

Срез готов, когда выполнимо вживую:

1. Открыть `localhost`, увидеть холст редактора.
2. Создать узлы (System / Container / Component), задать им `parentId`, провести связи.
3. Заполнить семантику узла, включая LLM-поля (`invariants`, `assumptions`, `failureModes`, `responsibilities`, `purpose`).
4. Сохранить — на диске лежит валидный `hyphae.json` с непустыми `nodes`/`connections`/`views` и пустыми зарезервированными коллекциями.
5. Подключить MCP-сервер к Claude Code, вызвать `get_text_context` — получить компактный читаемый текст модели.
6. Реальная проверка ценности: дать агенту задачу по коду проекта, где контекст из модели помогает, и увидеть, что помогает.

Пункт 6 — это и есть подтверждение/опровержение гипотезы.

**Как тестируем успех: dogfood.** Это личный проект — формальные A/B-батареи и метрики не нужны. Единственный тест: смоделировать архитектуру самого Hyphae в Hyphae, затем строить последующие фазы (zoom-навигация, flows...) с подключённым MCP-контекстом своей же модели. Сигнал успеха — субъективный, но честный для соло-юзера: реально ли модель помогает агенту, окупается ли её ведение, не дрейфует ли она от кода. Непрерывный фон с момента готовности среза, не разовый прогон.

## 3. Scope IN — что входит

### 3.1 Схема (`packages/schema`, Zod)

- **Полная модель верхнего уровня с дня 1** (MODEL_RU §8): `nodes`, `connections`, `views` + зарезервированные **пустые** коллекции `flows`, `stateMachines`, `dataTypes`, `requirements`, `decisions`. Резерв ничего не стоит и убирает дорогую миграцию позже.
- `schemaVersion` присутствует с первого дня.
- **Node** — вся идентичность, семантика, метаданные, `parentId`, `codeRefs`/`docRefs` (plain strings), и **LLM-поля как first-class**: `invariants`, `assumptions`, `failureModes`, `responsibilities`, `purpose`. Это топливо для ценности — не режем.
- **Connection** — first-class, тип расщеплён на три ортогональных поля: `relationCategory` (Dependency | DataFlow | Realization | Trace), `transport` (Sync | Async | InProcess | None), `intent` (опц.). Прочие поля (`protocol`, `direction`, `frequency`, `latencyBudgetMs`, `security`, `realizes`, `dataTypeRef`) — **в схеме есть, в UI редактора позже**.
- **`parentId` containment** работает: System → Container → Component.
- **Профиль `c4-backend` как данные** (объект profile, не хардкод в коде): движок читает словарь типов и containment-правила из профиля. Профиль один, но механизм профилей настоящий → новый профиль потом не ломает ядро.
- JSON Schema автогенерируется из Zod (`zod-to-json-schema`).

### 3.2 Сервер (Hono, Node 22+)

- `GET /model`, `PUT /model`.
- Атомарная запись: `hyphae.json.tmp` → `rename`. Debounce 500ms на сохранения (drag и т.п.).
- Один JSON-файл на диске. Без облака, без аутентификации.
- В prod отдаёт собранный SPA из `apps/web/dist`.

### 3.3 Редактор (Vite + React 18 + TS + React Flow + Zustand)

- Один холст. Узлы и связи: create / delete / drag.
- **Слой = dropdown-фильтр** (Context / Container / Component), НЕ zoom drill-down. Containment живёт в данных, навигация по слоям — простой фильтр.
- **Side-panel** при выделении: все поля узла. LLM-семантика (`invariants`, `assumptions`...) — first-class в панели, не спрятана в «advanced».
- Позиции нод сохраняются в `views`.
- Rough-but-functional: цель — функция, не полировка drag-UX.

### 3.4 MCP-сервер (read-only)

- Локальный MCP-сервер, подключается к Claude Code / другому MCP-клиенту.
- Тулы: `get_text_context`, `get_node`, `list_nodes`, `find_connections`.
- `get_text_context` — тонкая обёртка над **чистой функцией `getContext(scope)`**, которая рендерит граф в компактный plain text (читается LLM лучше сырого JSON). Чистота функции важна: позже MCP write-tools и другие каналы переиспользуют тот же рендер.
- `describe_flow` — **вне среза** (flows нет).

## 4. Scope OUT — что режем из текущего MVP

| Режем | Откуда | Почему |
|-------|--------|--------|
| Flows (создание, overlay, sequence-view) | SPEC фаза 3 | Отдельная ось Поведение. Гипотеза среза доказывается без неё. |
| Zoom drill-down + breadcrumbs + cross-layer view | SPEC фаза 2 | Дорогой UX. Containment живёт в данных; навигация = dropdown-фильтр. |
| Редакторы зарезервированных осей (state machines, data types, requirements, decisions) | SPEC фаза 7+ | Схема есть с дня 1, UI приходит позже. |
| Опциональные поля связи в UI | — | В схеме есть, в редакторе позже. Не доказывают гипотезу. |
| Полиш drag-drop, dagre auto-layout | SPEC §10 | Не двигает гипотезу. |
| `describe_flow` MCP-тул | SPEC фаза 4 | Нет flows. |
| Code binding, drift, write-tools | SPEC фазы 5-6 | За горизонтом среза. |

**Состав среза ≈** фаза 1 + containment-данные из фазы 2 + read-only MCP из фазы 4. Узкий по ширине, полный по глубине (до LLM).

## 5. Структура репо (как в SPEC §10)

```
hyphae/
  apps/
    web/        # Vite + React редактор
    server/     # Hono backend + MCP-сервер
  packages/
    schema/     # Zod-схемы + типы + JSON Schema + профиль c4-backend
  hyphae.json   # модель (или рядом с проектом пользователя)
```

Пакетник — pnpm workspaces. `pnpm dev` поднимает оба процесса.

## 6. После среза (порядок наращивания)

Когда гипотеза подтверждена, наращиваем по SPEC roadmap. Естественный следующий слой:

1. Zoom-навигация между слоями (богатый UX поверх уже работающего containment).
2. Flows (ось Поведение, overlay + sequence-view).
3. MCP write-tools (LLM правит модель, человек ревьюит).
4. Code binding (tree-sitter, drift detection).

Срез намеренно оставляет эти точки роста открытыми и не закрывает их ранними решениями (профиль как данные, чистая `getContext`, полная схема с дня 1).
