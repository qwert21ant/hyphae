00 The one decision

Continuo

Derived from the model: a module is game-facing when it, or a component inside it, has an edge to one of the two Minecraft clients. Two of the nine modules do. Everything on this page is tinted by that split.

The two laws the system states about itself

What it is accountable for

    The two clients

    The model names two external systems. They are the only things outside Continuo's ownership, and they are the reason the rest of the page is shaped the way it is.

    Continuo has nine containers.

    02 The walk

    One key press, thirteen steps

    A flow in this model is an ordered list of steps; each step names the node it starts at, the node it reaches, and — usually — the connection it travels along. Continuo has exactly one behaviour today, and the model records it twice: once at component scope and once at container scope.

    Every node below is introduced the first time the walk touches it. Thirteen of the model's 49 nodes are on this path; the sections after it pick up the rest.

    The same walk, one altitude up

    The model carries a second flow over the same behaviour, at container scope, so it can be followed without knowing any component names. Nine steps instead of thirteen, and no new facts — but it is where the tick arrives from the game as an async step rather than appearing from nowhere.

    03 Inside the search

    What step 9 was advancing

    Step 9 handed a slice of work to the and step 10 got a finished segment back. That is the whole of the executor's view of pathfinding. Underneath it, the Pathfinder module is six components with one job between them: turn a start, a goal and a block source into a route, without ever touching the game.

    How they are wired to each other

    Seven edges inside the module. Nothing here reaches outside the Pathfinder except through the block source and the movement registry.

    04 What a movement is

    The seam a jump plugs into

    The search does not know how to walk. It asks the movement registry which movements are active under the capabilities its caller granted, and each movement offers the neighbours it can reach. Everything a movement needs is published in its own module — deliberately, so that a movement can be written without seeing the search at all.

    The proof: a jump that lives outside the core

    The model contains one module whose entire stated purpose is to demonstrate that the seam holds. It is a separate container with a single component, found at runtime, named nowhere in the core.

    05 What the search reads

    A block stops being a version

    Step 8 wrapped the live world in a snapshot. That snapshot sits at the end of a four-stage read path: the shipped override tables, the classifier that applies them, the reader that memoises one classification per block state, and the per-search copy the search actually talks to. This is the Core module, and it is where a version-specific block state becomes a fact the rest of the system can reason about.

    The two remaining Core components

    Core also holds two contracts that are not about blocks at all — they live here because Core is the lowest module that both sides can see.

    06 The contract

    Five interfaces and four rules

    Everything the core is ever allowed to know about Minecraft is written down in one module at the bottom of the ladder. It is deliberately small: the model states that every type added here becomes a compatibility obligation on every future adapter, which is why testing seams were kept out of it and put on the core side instead.

    The four global rules

    The SPI states four rules by number, and the numbering is load-bearing — the model says the conformance suite depends on it. Two of them are the state machine you met at step 3; the fourth is why the executor restates every input on every tick rather than remembering what it pressed.

    07 The second adapter

    The same three parts, fourteen years apart

    The whole architecture exists so that supporting another Minecraft version is a new adapter rather than a fork. The model carries two, and they have identical internal shapes: an entrypoint, a set of platform bindings, and a dev-only diagnostics surface. What differs is written down per side.

    08 Instruments

    The parts that exist because a test cannot get there

    Adapter code cannot be tested headlessly — a live block view and a live player have no offline substitute. The model answers that with four dev-only components and one renderer, none of which is on the walk's path except for the one that holds the marked goal.
