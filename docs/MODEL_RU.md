# Hyphae — Концепция модели

> Как Hyphae описывает **любой** проект малым набором сущностей, без избытка и дублей, удобно человеку и LLM. Этот документ — про модель (мета-уровень). Продукт, scope, реализация — в [SPEC_RU.md](./SPEC_RU.md).

---

## 1. Проблема и установка

C4 описывает 2 вещи: статическую структуру (что из чего состоит) и статические зависимости (кто кого знает). Этого мало, чтобы описать произвольный проект: нет поведения во времени, нет домена данных, нет «зачем» (требований и решений). А frontend / CLI / desktop вообще плохо ложатся на словарь System/Container/Component.

Соблазн — добавить под каждый случай свою диаграмму (ERD, state chart, component tree, user-journey...). Это ведёт к зоопарку сущностей и дублям (одно и то же выражается разными способами).

**Установка Hyphae:**

1. Любой проект описывается **малым набором ортогональных осей**. Диаграмма = проекция одной-двух осей, а не отдельная сущность.
2. **Механизмы универсальны, словарь типов — профилируется.** Узел, ребро, поток, машина состояний, трассировка, view работают одинаково для сервера, фронта, CLI. Меняется только vocab типов узлов (профиль).
3. **Анти-избыточность как правило:** новая first-class сущность вводится, только если её надо адресовать/линковать независимо. Иначе это поле.

## 2. Шесть осей описания

Оси ортогональны — каждая отвечает на свой вопрос. Проект = срез по нескольким осям одновременно.

| Ось | Вопрос | Носители в модели | Проекции (диаграммы) |
|-----|--------|-------------------|----------------------|
| **Структура** | из чего состоит | `parentId` узлов | C4 containment, UI-tree, module-tree |
| **Зависимости** | кто кого знает/использует | связи `type: Dependency` | граф зависимостей |
| **Поведение** | что происходит во времени | `flows`, `stateMachines` | sequence, state chart, activity |
| **Данные** | какими сущностями оперирует | `dataTypes` + связи DataFlow | ERD, data-flow |
| **Интент** | зачем, какие требования/решения | `requirements`, `decisions` + связи `Trace` | traceability matrix, decision map |
| **Презентация** | как это смотреть | `views` | layouts, фильтры |

Ключевая мысль: **диаграмм много, осей мало.** Sequence и state chart — обе ось Поведение. ERD — проекция оси Данные. Traceability matrix — проекция оси Интент. Не нужно N типов сущностей под N диаграмм.

## 3. Универсальные механизмы (ядро)

Не зависят от профиля. Всегда одинаковые.

### 3.1 Node (узел)
Любая адресуемая сущность модели. **Ядро узла лёгкое и не зависит от профиля:**
`id`/`name`/`type`/`description`/`parentId` (структура)/`codeRefs`/`docRefs`/`createdAt`/`updatedAt` и
мешок `fields` (доменные значения). Всё доменно-специфичное (`responsibilities`, `invariants`,
`technology`, …) — это **поля профиля**, лежащие в `fields` и валидируемые против активного профиля.
Конкретные **типы** узла берутся из профиля; `layer`/`category` выводятся из `type`.

### 3.2 Connection (связь)
First-class ребро. Ядро: `id`/`from`/`to`/`type`/`description`/`direction`/`realizedBy` (cross-layer)/`codeRefs`
и мешок `fields`. **`type` — это вид связи (ConnectionKind) из профиля** (`Dependency` | `DataFlow` |
`Realization` | `Trace` в `c4-backend`); он заменил прежний `relationCategory`.

Прежние ортогональные оси связи стали **полями профиля** в `fields` (с описанием каждого значения для
LLM): `transport` (`Sync`/`Async`/`InProcess`/`None`) и `intent` (`Read`/`Write`/`Trigger`/`Notify`/`Use`).
Профиль может задать и другие поля на конкретном виде связи (напр. `dataTypeRef` на `DataFlow`).

> `Composition` когда-то был отдельным видом — удалён; структура живёт только в `parentId`.

### 3.3 Flow (поток)
Упорядоченный сценарий поверх узлов и связей. Overlay, не отдельная диаграмма. Шаги с `control` (alt/opt/loop/par) для ветвления. Ось Поведение, «горизонтальное» время.

### 3.4 StateMachine (машина состояний)
Привязана к узлу. states + transitions {from, to, trigger, guard, effect}. Ось Поведение, «жизненный цикл». Покрывает протоколы, домен (статус заказа), UI-режимы.

### 3.5 View (вид)
Сохранённая настройка просмотра: слой, фильтр, ручной layout. Ось Презентация. Truth — структура; view — presentation.

> Эти пять механизмов + профили описывают всё. Новый тип проекта = новый профиль, не новый механизм.

## 4. First-class сущности

Сущность first-class, если на неё ссылаются независимо (по `id`). Полный список:

| Сущность | Ось | Зачем first-class |
|----------|-----|-------------------|
| **Node** | Структура / Зависимости | базовый адресуемый блок |
| **Connection** | Зависимости / Данные / Интент | связь несёт семантику, не просто стрелка |
| **Flow** | Поведение | сценарий переиспользует узлы/связи |
| **StateMachine** | Поведение | lifecycle адресуется отдельно от узла |
| **DataType** | Данные | тип переиспользуется многими узлами/связями |
| **Requirement** | Интент | требование трассируется к многим узлам |
| **Decision (ADR)** | Интент | решение затрагивает многие узлы |
| **View** | Презентация | именованный сохранённый вид |

**Что НЕ first-class (поля профиля, не сущности):**
- `responsibilities`, локальные `invariants`, `technology`, `transport`, `intent` и т.п. — **поля
  профиля** в `fields`-мешке узла/связи, а не отдельные сущности. (Cross-cutting инвариант →
  становится Requirement.)
- containment — `parentId`, не сущность-связь.
- позиции нод — внутри View.

Граница простая: **«нужно ли ссылаться на это из другого места?»** Да → сущность. Нет → поле.

## 5. Профили (словарь типов)

Профиль — декларативный словарь типов узлов и правил для конкретного класса проектов. Меняет vocab, не механизмы.

Профиль теперь — это **мета-схема**: он объявляет виды узлов, виды связей и их **поля** (с описанием
каждого поля и каждого enum-значения — в основном для LLM и тултипов редактора).

```
Profile {
  id
  layers: [...]                         // упорядоченные уровни профиля
  nodeKinds: [
    { id, category: Structure|Behavior|Data|Intent|Actor,
      layer, allowedParents:[...], allowedChildren:[...],
      fields: [FieldDef] }              // доменные поля этого вида узла
  ]
  connectionKinds: [
    { id, description, allowedFrom?:[...], allowedTo?:[...], fields:[FieldDef] }
  ]
  commonNodeFields:       [FieldDef]    // применяются ко всем видам узлов
  commonConnectionFields: [FieldDef]    // применяются ко всем видам связей
}

FieldDef {
  key, label?,
  type: text|number|boolean|list|enum|ref,
  description,                          // обязательно — для LLM/редактора
  required?,
  values?: [{ value, description }],    // для enum: каждое значение описано
  refKind?                              // для ref: на какой вид узла ссылается
}
```

Эффективные поля вида = `common*Fields`, затем собственные `fields`; **общие выигрывают** при
совпадении ключа (`effectiveFields(profile, kindId, scope)`). `layer`/`category` узла **выводятся**
из `type`. Значения полей хранятся в `fields`-мешке узла/связи и **строго валидируются** против
профиля (неизвестный ключ, неверный тип, недопустимое enum-значение, отсутствие required, висячий
ref — всё это отвергается).

### Примеры профилей

| Профиль | Уровни / типы узлов |
|---------|---------------------|
| **c4-backend** (MVP) | Landscape · Context (System, Actor, ExternalSystem) · Container · Component · Code |
| **frontend** | App · Route · View/Page · UIComponent · Store · Hook · Service |
| **cli** | Program · Command · Subcommand · Flag · Arg · Handler |
| **desktop** | App · Window · Panel · Menu · Action · Service |

Все профили используют одни и те же Connection / Flow / StateMachine / DataType / Requirement / View. Например, frontend-навигация = Flow поверх Route-узлов; UI-режимы экрана = StateMachine; форма ↔ DTO = `dataTypeRef` на связи. Никакого спец-движка под фронт.

LLM-friendliness сохраняется: словарь типов всё ещё **закрытый и конечный** — он просто декларативный, а не зашитый в код.

## 6. Traceability — почему это главное для LLM

Оси связываются сквозной трассировкой. Это превращает модель из «картинок» в проверяемый граф знаний:

```
Requirement ──Trace──> Node ──codeRefs──> код
Decision    ──Trace──> Node                (почему так)
Flow.steps  ──via────> Connection          (сценарий → связи)
Connection  ──realizedBy──> Connection     (верхний слой → нижний)
Node        ──parentId──> Node             (структура)
Connection  ──dataTypeRef──> DataType      (что передаётся)
StateMachine ──привязка──> Node            (жизненный цикл)
```

Что даёт LLM-агенту:
- «Какие требования реализует компонент X и где это в коде» — обход `Trace` → `codeRefs`.
- «Требование Y объявлено, но ни один узел его не реализует» — пробел в покрытии.
- «Почему компонент устроен так» — связанные Decision-узлы.
- «Что сломается при изменении связи A→B» — `realizedBy` вниз + flows, использующие её.

Это и есть смысл многоосевой модели: не нарисовать красивее, а сделать архитектуру **запрашиваемой и проверяемой**.

## 7. Принципы анти-избыточности

Правила, удерживающие модель от разрастания и дублей:

1. **Одна правда на факт.** «Из чего состоит» — только `parentId` (Composition-связь удалена). Схема данных на связи — только `dataTypeRef` (не inline-строка).
2. **Сущность только если адресуема.** См. §4. Иначе — поле.
3. **Расщеплять перегруженные enum'ы по ортогональным осям.** Связь: природа / транспорт / намерение — три поля, не один.
4. **Диаграмма ≠ сущность.** Новая визуализация — это проекция существующих осей, а не новый тип данных.
5. **Тип проекта = профиль, не движок.** Не добавлять frontend-специфичные сущности; выразить через общие механизмы + профиль.
6. **Локальное inline, глобальное — узел.** Инвариант одного узла — поле; cross-cutting — Requirement.

## 8. Полная модель (структура верхнего уровня)

```
HyphaeModel {
  schemaVersion
  metadata { name, description, createdAt, updatedAt }
  activeProfile                 // id профиля
  nodes:         [Node]         // Структура + Зависимости
  connections:   [Connection]   // Зависимости / Данные / Интент
  flows:         [Flow]         // Поведение (горизонтальное)
  stateMachines: [StateMachine] // Поведение (lifecycle)   — резерв в MVP
  dataTypes:     [DataType]     // Данные                  — резерв в MVP
  requirements:  [Requirement]  // Интент                  — резерв в MVP
  decisions:     [Decision]     // Интент                  — резерв в MVP
  views:         [View]         // Презентация
}
```

«Резерв в MVP» = коллекция существует в схеме с первого дня (пустой массив), редактор/визуализация приходят на фазе 7+. Так оси заложены без дорогой миграции — см. roadmap в [SPEC_RU.md](./SPEC_RU.md).
