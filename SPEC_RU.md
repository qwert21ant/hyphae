# Hyphae — Specification

> Визуальный редактор многомерной модели архитектуры кода и knowledge base для LLM-агентов. Долгосрочная цель — bidirectional sync между моделью и кодом.

> Концепция модели (оси, first-class сущности, профили) вынесена в отдельный документ: **[MODEL_RU.md](./MODEL_RU.md)**. Этот файл — про продукт, scope и реализацию.

---

## 1. Vision

Hyphae превращает архитектуру программной системы из устаревающей документации в живую модель, доступную одновременно человеку (визуальный редактор) и LLM (структурированный формат + MCP). Конечная цель — обратный флоу: пользователь правит модель верхнего уровня → AI каскадно перестраивает нижние уровни → AI переписывает код под новую структуру.

Принципиальная установка: модель должна описывать **любой** тип проекта — серверное приложение, frontend (view, компоненты, стор), CLI, desktop — а не только C4-style backend. Достигается это не зоопарком диаграмм, а малым набором **ортогональных осей описания** (структура, зависимости, поведение, данные, интент, презентация) поверх универсальных механизмов. Тип проекта меняет только **словарь типов узлов** (профиль), а движок — рёбра, потоки, машины состояний, трассировка, views — общий. Детали — в [MODEL_RU.md](./MODEL_RU.md).

Метафора в имени: hyphae — нити грибницы. Невидимая ткань, соединяющая код, архитектурное знание и AI-агентов.

---

## 2. Цели MVP

- Визуальный редактор многоуровневых диаграмм с гибким drag-and-drop UX (профиль `c4-backend` как первый).
- Привязанные к модели Flow-диаграммы (sequence-подобные сценарии поверх существующих узлов и связей).
- Единая структурированная модель (JSON) — single source of truth для всех views.
- Схема, заложенная под многоосевую модель и профили **с первого дня** (даже если активен один профиль), чтобы не платить за миграцию позже.
- Формат и метаданные, оптимизированные под потребление LLM.
- Локальный запуск без облака и аккаунтов.

## 3. Не-цели MVP

Откладывается явно, чтобы не раздуть scope. Важно: часть из этого — **полноценные оси модели** (см. MODEL_RU.md), они зарезервированы в схеме как пустые коллекции, но редактор/визуализация для них приходят позже.

- Code binding — автопарсинг кода (tree-sitter, AST), связывание узлов с символами.
- LLM-driven editing — запись в модель через AI. На MVP LLM только читает.
- Реалтайм-коллаборация (CRDT, multi-cursor).
- Машины состояний (ось Поведение) — схема зарезервирована, редактор позже.
- Domain/Data-модель (ось Данные, ERD-проекция) — схема зарезервирована, редактор позже.
- Requirements / Decisions (ось Интент, traceability) — схема зарезервирована, редактор позже.
- Профили кроме `c4-backend` (frontend / cli / desktop) — модель поддерживает, готовые профили доезжают позже.
- Deployment / infra views.
- Code-level визуализация как граф классов.
- Drift detection, метрики, hotspots.

---

## 4. Целевой пользователь

Solo-разработчик + AI-агент как co-user. Сценарии:

- Разработчик ведёт модель своего проекта вручную через визуальный редактор.
- AI-агент (Claude Code или похожий) читает модель как контекст перед изменением кода.
- На последующих фазах AI правит модель, человек ревьюит изменения.

Командные сценарии (shared workspace, comments, drafts) — out of scope для MVP, но хранение (JSON-файл) совместимо с Git, поэтому базовая коллаборация через git diff/merge возможна с первого дня.

---

## 5. Архитектура системы (high-level)

Локальное веб-приложение по модели Structurizr Lite:

- Один процесс — локальный Node-сервер.
- Frontend — SPA, открывается в браузере на `localhost`.
- Backend — обслуживает API и отдаёт собранный bundle.
- Persistence — один JSON-файл на диске.
- Без внешних сервисов, без облака, без аутентификации в MVP.

## 6. Модель данных

> Полная концепция (оси, категории, профили, анти-избыточность) — в [MODEL_RU.md](./MODEL_RU.md). Ниже — операционный срез: что хранится и что редактируется в MVP.

### 6.1 Профили и слои

Слой узла — не глобальный хардкод-enum, а производное от **профиля** + категории узла. Профиль — декларативный словарь: какие типы узлов существуют, кто чей родитель (containment-правила), какая у узла категория (Structure / Behavior / Data / Intent / Actor).

MVP активирует один профиль — `c4-backend`:

| Уровень | Описание | MVP |
|---------|----------|-----|
| Landscape | Несколько систем в экосистеме | Нет |
| Context | Система + внешние акторы и системы | Да |
| Container | Deployable units внутри системы | Да |
| Component | Логические building blocks внутри контейнера | Да |
| Code | Классы / функции — proxy-слой (ссылки на код) | Нет (фаза 5) |

Фиксированный словарь (а не свободная декларация слоёв) сохраняется ради LLM-friendliness — но теперь это свойство профиля, а не движка. Будущие профили (frontend / cli / desktop) задают свои уровни и типы, не трогая ядро.

### 6.2 Узлы (Nodes)

Каждый узел имеет:

**Идентичность:**
- `id` — stable UUID или slug, не меняется при переименовании.
- `name` — человекочитаемое имя.
- `type` — тип из активного профиля (в `c4-backend`: System | Container | Component | Actor | ExternalSystem | Code).
- `layer` / `category` — выводятся из профиля по типу.

**Семантика:**
- `description` — свободный текст, основное описание.
- `responsibilities` — массив строк. Локальный список обязанностей. Может ссылаться на узлы Requirement (ось Интент), когда обязанность адресуема глобально.
- `purpose` — короткое summary (tooltip, LLM-контекст).
- `technology` — стек.
- `tags` — массив тегов.

**Семантика для LLM:**
- `invariants` — массив локальных инвариантов (что всегда выполняется для этого узла). Cross-cutting инварианты живут как отдельные Requirement-узлы.
- `assumptions` — предположения о среде, входах, поведении внешних систем.
- `failureModes` — известные режимы отказа.

**Метаданные:**
- `owner` — опционально.
- `status` — Planned | Active | Deprecated.
- `createdAt`, `updatedAt`.

**Линки:**
- `codeRefs` — ссылки на код (file path + symbol). В MVP — plain strings, парсятся в фазе 5.
- `docRefs` — ссылки на внешние документы / ADR.

**Иерархия:**
- `parentId` — ссылка на родителя по правилам containment профиля. **Единственный** носитель «из чего состоит» (никакой Composition-связи, см. 6.3).

### 6.3 Связи (Connections / Edges)

Связь — first-class сущность, не просто стрелка.

**Идентичность:**
- `id`, `from` (node id), `to` (node id).

**Тип — три ортогональных поля** (вместо одного перегруженного enum; устраняет category error прежней версии):
- `relationCategory` — Dependency | DataFlow | Realization | Trace. Чем связь является по природе.
- `transport` — Sync | Async | InProcess | None. Механизм (для runtime-связей).
- `intent` — Read | Write | Trigger | Notify | Use (опционально). Намерение.

> `Composition` удалён — containment выражается только `parentId`. Никакого дубля «состоит из».

**Семантика:**
- `description` — что связь делает.
- `protocol` — HTTP, gRPC, AMQP, in-process.
- `dataTypeRef` — опц. ссылка на узел DataType (ось Данные), которым связь оперирует. Заменяет прежний inline `dataSchema: string`.
- `direction` — Unidirectional | Bidirectional.

**Атрибуты:**
- `frequency` — Rare | Occasional | Frequent | Continuous.
- `latencyBudgetMs` — опционально.
- `security` — { authRequired, encryption }.

**Линки:**
- `codeRefs` — где реализуется (фаза 5).
- `realizes` — массив id связей нижнего уровня, реализующих эту связь (cross-layer realization).

### 6.4 Flows

Flow — упорядоченная последовательность шагов поверх существующих узлов и связей. Не самостоятельная диаграмма, а overlay.

**Структура:**
- `id`, `name`, `description`.
- `scope` — на каком слое разворачивается (обычно Container или Component).
- `steps` — упорядоченный массив:
  - `order` — порядковый номер.
  - `from` — node id (или actor).
  - `to` — node id.
  - `via` — connection id (опц.; если указано — шаг привязан к существующей связи).
  - `message` — описание сообщения / вызова.
  - `kind` — Sync | Async | Return.
  - `control` — опц. { type: alt | opt | loop | par, condition } для ветвления/циклов/параллелизма (sequence-диаграммы умеют это; линейный список — частный случай).

**Инвариант:** все `from`, `to`, `via` обязаны существовать в модели. При удалении узла/связи затронутые flows помечаются `invalid` и подсвечиваются в UI.

### 6.5 Связи между слоями

Два механизма работают одновременно:

**Containment (`parentId` у узла):** Component → Container → Context system. Reverse-навигация: у Container получить все Component'ы.

**Realization (`realizes` у связи):** связь Container-уровня A→B реализуется множеством связей Component-уровня внутри A и B. Опционально; если заполнено — проверяется консистентность.

### 6.6 Зарезервированные оси (схема с дня 1, редактор позже)

Эти коллекции присутствуют в модели как (возможно пустые) массивы с MVP — ради будущих миграций без боли. Концепция каждой — в [MODEL_RU.md](./MODEL_RU.md).

- `dataTypes` — **ось Данные.** Узлы-типы домена (Entity | Value | Event | DTO) с полями. ERD = проекция связей produces/consumes/persists.
- `stateMachines` — **ось Поведение.** Машина состояний, привязанная к узлу (lifecycle, протокол, UI-режимы): states + transitions {from, to, trigger, guard, effect}.
- `requirements` — **ось Интент.** Узлы требований (Functional | Quality | Constraint). Трассируются от узлов/flows через связи `relationCategory: Trace`.
- `decisions` — **ось Интент.** ADR-узлы (context / choice / consequences / status), линкуются к затронутым узлам.

### 6.7 Views

View — именованная сохранённая «настройка просмотра»:
- На каком слое.
- Какие узлы и связи показывать (фильтр по тегам / containment).
- Координаты ручного layout каждого узла.

Views хранятся в той же модели. Truth — структура; views — presentation.

## 7. Формат хранения

**Один JSON-файл** — single source of truth.

```
project-root/
  hyphae.json     # модель целиком
```

**Атомарная запись:**
- Backend пишет в `hyphae.json.tmp`, затем `rename` → `hyphae.json`.
- Debounce 500ms между запросами на сохранение (drag и т.п.).

**Schema:**
- JSON Schema автогенерируется из Zod-схем через `zod-to-json-schema`.
- Опц. включается в `$schema` файла — для валидации в редакторах.

**Git-friendly:**
- Детерминированный порядок ключей.
- Пользователь сам решает, коммитить ли в репо проекта.

**Индекс (фаза 4+):**
- При старте JSON грузится в in-memory граф для query-нагрузки.
- Позже — опц. SQLite-кэш для больших моделей.

## 8. LLM-friendliness — design principles

Отличительная фича Hyphae, заложена в core:

- **JSON Schema как контракт.** Zod-схемы — источник истины. Из них: TS-типы эдитора, JSON Schema для валидации, OpenAPI для API, инструменты MCP.
- **Stable IDs у всего.** LLM ссылается на конкретный узел между сообщениями.
- **Свободный текст + структурированные поля.** `description` — семантика, `responsibilities` / `invariants` / `assumptions` — адресуемая структура.
- **Traceability как граф.** Requirement ↔ Node ↔ Code через связи `Trace`/`realizes`/`codeRefs`. LLM ходит «требование → компонент → код» — проверить реализацию, найти пробелы. Главная ценность многоосевой модели для AI.
- **Текстовый экспорт.** `getContext(scope)` рендерит граф в компактный plain text для prompt — читается LLM лучше JSON.
- **MCP-сервер (фаза 4).** Read-only на старте: `get_node`, `list_nodes`, `find_connections`, `describe_flow`, `get_text_context`. Write-tools — фаза 6.
- **Inline-описания, не отдельные файлы.** LLM работает с одним документом лучше, чем с россыпью.

---

## 9. UX-принципы

- **Model-first.** Пользователь правит структуру, диаграммы — views. Позиции нод в каждой view — visual hint, не truth.
- **Один шаг — одна операция модели.** Drag компонента в другой контейнер = смена `parentId`. Удаление узла = инвалидация связей и flows, явно подсвеченных в UI.
- **Zoom-навигация между слоями.** Double-click по контейнеру → Component-view контейнера. Breadcrumbs сверху.
- **Flow как overlay.** Включаешь flow → на текущем view подсвечиваются связи в порядке шагов.
- **Все поля узла в side-panel** при выделении. Семантические поля для LLM (`invariants`, `assumptions`) — first-class, не «advanced».

## 10. Технологический стек

### Frontend
- **Vite** + **React 18** + **TypeScript**
- **@xyflow/react** (React Flow) — node-based editor
- **Zustand** — стейт эдитора
- **Tailwind CSS** — опц., для скорости стилизации
- **dagre** — опц. auto-layout

### Backend
- **Node 22+** (или Bun)
- **Hono** — веб-фреймворк (Fastify — альтернатива)
- **Zod** — валидация и schema definition

### Shared
- Пакет `@hyphae/schema` с Zod-схемами как источником истины.
- Из него: TS-типы для frontend/backend, JSON Schema через `zod-to-json-schema`.

### Структура репо
```
hyphae/
  apps/
    web/        # Vite + React frontend
    server/     # Hono backend
  packages/
    schema/     # Zod schemas + types + JSON Schema + профили
  hyphae.json   # модель (или живёт рядом с проектом пользователя)
```
Пакетник — **pnpm workspaces**.

### Dev workflow
- `pnpm dev` запускает оба процесса.
- В dev frontend на Vite-dev-сервере, backend проксирует API.
- В prod backend отдаёт собранный SPA из `apps/web/dist`.

### Решения, экономящие время
- Не Redux. Zustand/Jotai проще для node-эдитора.
- Не писать JSON Schema руками. Zod → `zod-to-json-schema`.
- Не писать свой layout-движок. React Flow + manual + dagre.
- REST достаточно для MVP. WebSocket — когда появится фоновый AI-агент.

## 11. Phased roadmap

### Фаза 1 — MVP редактор (2–4 недели)
- Zod-схемы: узлы, связи, flows, профили; зарезервированные пустые коллекции (dataTypes/stateMachines/requirements/decisions).
- Сервер: `GET/PUT /model` (атомарная запись).
- React Flow эдитор для одного слоя — Component.
- Side-panel для всех полей узла.
- Сохранение позиций нод в views.

### Фаза 2 — Многоуровневость (2–3 недели)
- Слои Context, Container, Component (профиль `c4-backend`).
- Zoom-навигация (double-click drill-down, breadcrumbs).
- Containment (`parentId`).
- Cross-layer view: «все компоненты этого контейнера».

### Фаза 3 — Flows (2–3 недели)
- Создание flows: выбор узлов и связей, добавление шагов, control-структуры (alt/opt/loop/par).
- Визуализация поверх view (подсветка + порядковые номера).
- Sequence-style view (вертикальная диаграмма) как альт-режим.

### Фаза 4 — MCP-сервер для AI (read-only)
- Инструменты: `get_node`, `list_nodes`, `find_connections`, `describe_flow`, `get_text_context`.
- Локальный MCP-сервер, подключается к Claude Code / др. MCP-клиенту.
- Первый момент, когда Hyphae становится тем, ради чего затевался — AI-friendly knowledge base.

### Фаза 5 — Code binding
- `codeRefs` валидируются: ссылается ли файл/символ на существующую точку.
- Парсер на tree-sitter (`web-tree-sitter` в Node).
- Computed Code-слой: автогенерация классов/функций из кода с привязкой к Component.
- Drift detection: компоненты без реализации, классы без отражения в модели.

### Фаза 6 — LLM editing (write-tools в MCP)
- Инструменты записи: `update_node`, `add_connection`, `add_flow`, `rebind_code`.
- AI предлагает изменение модели — пользователь ревьюит как PR-like diff.
- Reverse flow: пользователь правит модель → AI генерирует план изменений кода → применяет.

### Фаза 7+ — отложенное
- Активация осей Поведение / Данные / Интент в редакторе (схема уже есть с фазы 1).
- Профили frontend / cli / desktop.
- Multi-system landscape.
- Реалтайм-коллаборация (Yjs / CRDT).
- Deployment / infra views.
- Метрики, hotspots, drift dashboards.

## 12. Открытые вопросы

- **Code-слой: ноды или граф?** На фазе 5 решить: рисуем Code как полноценный граф классов или держим Code-узлы «прикреплёнными» к Component'ам без отдельного view.
- **Granularity flow.** Шаг = вызов метода или логическое действие? Возможно, оба, с уровнем детализации как параметром.
- **Профили: встроенные или плагины?** Останутся ли frontend/cli/desktop встроенными словарями или станут загружаемыми плагинами с собственными валидаторами.
- **Multiple files vs single file.** Когда модель станет большой — разбивать по системам/контейнерам? Откладывается до того, как станет проблемой.
- **Версионирование внутри файла.** `schemaVersion` в `hyphae.json` с первого дня — для миграций.
- **Конфликты merge в Git.** Два изменения одного узла → JSON-конфликт. Решение — детерминированный formatter + понятная структура +, в долгосроке, schema-aware merge-tool.
